# Целевая архитектура Clawd

Этот документ — целевая архитектура под рост до больших объёмов пользователей.
Приоритет: понятная модель для реализации и операционного сопровождения.

## 1) Продуктовая рамка

Базовые режимы маршрутизации:

- Без подписки: `client -> Clawdbot -> Ollama`
- С подпиской: `client -> Clawdbot -> API LLM` (Claude / GPT / Gemini)

Единая точка принятия решения — policy-слой в боте. Пользователь не выбирает технический маршрут вручную.

## 2) Архитектурные принципы

- Bot-воркеры stateless: горизонтальное масштабирование без sticky-сессий.
- Данные состояния/лимитов — только в Postgres/Redis.
- Один входящий запрос всегда проходит через единый `AccessDecision` (policy contract).
- Деградация контролируемая: при проблемах API или LLM — понятный fallback/ошибка, без «молчаливого» зависания.
- Наблюдаемость обязательна: latency, error rate, queue depth, cost counters.
- Разделение control plane и inference plane.

## 3) Логическая схема

```text
Telegram User
   |
   v
[Bot Ingress]
   |
   v
[Policy + Routing]
  |                   \
  |                    \
  v                     v
[Paid Path]          [Free Path]
 API LLM Adapter      Ollama Adapter
 (Claude/GPT/...)     (local/self-hosted)
  |                     |
  +----------+----------+
             v
      [Usage Metering]
             |
             v
   Postgres (users, plans, payments, usage)
   Redis (rate limits, counters, FSM, cache)
```

OpenClaw Gateway используется как оркестратор agent/tool-flow там, где это нужно по продукту.

## 4) Компоненты (целевая декомпозиция)

### 4.1 Bot Edge

Назначение:
- приём Telegram update;
- команды/кнопки/UX;
- валидация доступа;
- вызов policy + router;
- доставка ответа пользователю.

Свойства:
- без локального long-lived состояния;
- безопасно масштабируется N реплик.

### 4.2 Policy Service (внутри бота, затем можно вынести)

Назначение:
- решение маршрута `paid_api | free_ollama | deny`;
- применение квот и лимитов;
- приоритеты сегментов пользователей.

Контракт (логический):
- input: `user`, `plan`, `subscription_state`, `usage_snapshot`, `request_context`
- output: `provider`, `allowed`, `deny_reason`, `counters_to_increment`

### 4.3 Inference Adapters

- `ApiAdapter`: Claude/OpenAI/Gemini через операторские ключи.
- `OllamaAdapter`: локальный inference для free/fallback.
- `OpenClawAdapter` (опциональный слой): агентные сценарии, tools, skills, session management.

### 4.4 Metering & Billing Core

Назначение:
- учёт токенов и сообщений;
- биллинговый период;
- связь с платежами;
- выдача/снятие доступа.

Важно:
- metering делается централизованно после каждого ответа;
- idempotency ключи для webhook и повторных событий.

### 4.5 Storage

Postgres:
- пользователи/планы/периоды;
- платежи и статусы;
- usage ledger;
- настройки персонализации агента.

Redis:
- rate limit ключи;
- FSM;
- короткоживущие счётчики;
- кэш policy/config.

## 5) Целевой request flow

### 5.1 Paid path

1. User message -> Bot
2. Policy решает `paid_api`
3. Router вызывает API adapter (или OpenClaw->API)
4. Ответ + usage возвращаются
5. Metering фиксирует расход в периоде
6. Bot отправляет ответ

### 5.2 Free path

1. User message -> Bot
2. Policy решает `free_ollama`
3. Router вызывает Ollama
4. Bot отправляет ответ
5. Increment soft/trial counters

### 5.3 Failure handling

- Таймаут внешнего API -> controlled fallback (если политика разрешает)
- Таймаут Ollama -> пользователь получает короткий retry message
- Ошибки пишутся в structured logs + alert

## 6) Масштабирование по этапам

### Этап A (текущий / ближайший)

- Один VPS, docker-compose.
- Разделение логики в коде: `policy`, `adapters`, `metering`.
- Чёткие таймауты и retry budget.

### Этап B (100+ пользователей, умеренная одновременность)

- Увеличение compute: 8-16 vCPU, 16-32 GB RAM.
- Вынос тяжёлого пути в API LLM для paid.
- Ollama оставить для free/fallback.
- Добавить отдельные worker-процессы для async задач.

### Этап C (рост и пиковая нагрузка)

- Kubernetes или ECS-like оркестрация.
- Раздельные deployment для `bot`, `policy`, `openclaw`, `workers`.
- Managed Postgres/Redis.
- HPA по latency/CPU/queue depth.

## 7) SLO/SLI (целевые)

- SLI `reply_latency_ms` (p50/p95/p99) по каждому пути:
  - `paid_api`
  - `free_ollama`
  - `openclaw_agent`
- SLI `error_rate` по провайдерам.
- SLI `policy_denials` по причинам.
- SLI `cost_per_user_day` для API сегмента.

Базовые SLO (рабочая цель, можно корректировать):
- paid_api p95 < 12s
- free_ollama p95 < 25s
- error_rate < 1.5%

## 8) Обязательная наблюдаемость

Логи (structured JSON):
- request_id, user_id, route, provider, latency_ms, tokens_in/out, decision_reason.

Метрики:
- `llm_requests_total{provider,route,status}`
- `llm_latency_ms_bucket{provider,route}`
- `policy_decisions_total{decision,reason}`
- `billing_tokens_total{segment,provider}`

Трейсинг:
- Bot -> policy -> adapter -> provider request.

## 9) Безопасность и секреты

- API ключи LLM только в secrets (не в БД пользователя для v2 operator-key модели).
- Ротация ключей и аудит доступа.
- Отдельные роли для admin-команд.
- Минимизация PII в логах.

## 10) Решения по OpenClaw

OpenClaw в целевой схеме:
- используется как агентный runtime там, где нужны tools/skills/длинные workflows;
- не обязателен для каждого запроса (простые запросы могут идти напрямую в API adapter);
- для бесплатного пути по умолчанию не нужен (прямой Ollama быстрее и дешевле по накладным расходам).

Правило:
- OpenClaw включаем для сценариев, где его функциональность реально нужна (agent/tool orchestration),
  иначе идём более коротким маршрутом.

## 11) План внедрения без ломки текущего кода

1. Зафиксировать contract `AccessDecision` как единственный вход в routing.
2. Разделить adapters по явным интерфейсам (`ApiAdapter`, `OllamaAdapter`, `OpenClawAdapter`).
3. Ввести единый middleware metering после каждого ответа.
4. Добавить feature flags:
   - `ROUTE_PAID_VIA_OPENCLAW`
   - `ROUTE_FREE_VIA_OLLAMA`
   - `ENABLE_API_FALLBACK`
5. Добавить SLI метрики и алерты.
6. После стабилизации — вынос отдельных частей в сервисы.

## 12) Что не делаем сейчас (осознанно)

- Полный Kubernetes migration до появления стабильного продуктового трафика.
- Сложная multi-tenant skill sandbox из коробки.
- Глубокая кастомизация биллинга до утверждения тарифной математики.

## 13) Definition of Done для «архитектура готова к росту»

- Policy route детерминирован и покрыт тестами.
- Наблюдаемость позволяет ответить на вопрос «почему запрос медленный» за 5 минут.
- Paid/free пути изолированы и деградируют независимо.
- Смена провайдера (API <-> Ollama/OpenClaw) делается конфигом/feature flag, без рефакторинга хендлеров.
- Документация актуальна и отражает фактическую реализацию.

## 14) Продуктовая модель «Сделай за меня»

Целевой UX для нетехнического пользователя:

- Есть один главный агент (входная точка).
- Пользователь описывает задачу обычным языком.
- Главный агент сам создаёт и настраивает специализированных агентов под задачу.
- Пользователь ждёт завершения и получает готовый доступ/инструкцию.

Пользователь не должен работать с:
- BotFather токенами;
- group/topic ID;
- workspace/skills/symlink;
- gateway restart;
- ручной диагностикой конфигов.

### 14.1 Главный агент как Product Orchestrator

Главный агент в продукте выполняет роль оркестратора:

1. **Discovery** — собирает бизнес-цель и контекст.
2. **Template selection** — выбирает тип ассистента/сценария.
3. **Provisioning plan** — формирует план создания (агент, каналы, режимы, модель, правила).
4. **Execution** — запускает автоматическую настройку.
5. **Verification** — проверяет, что агент отвечает и доступен.
6. **Delivery** — отдаёт пользователю результат в понятном формате.

### 14.2 Обязательные backend-сущности

Нужны отдельные сущности поверх текущих `users`/`payments`:

- `provision_jobs` — очередь и статус создания/настройки агента.
- `provision_steps` — шаги выполнения и их результаты.
- `assistant_instances` — созданные ассистенты пользователя.
- `assistant_channels` — привязки к группе/топикам/режимам.
- `assistant_templates` — продаваемые шаблоны (контент, продажи, support и т.д.).

Базовые статусы `provision_jobs`:
- `queued`
- `running`
- `needs_input` (если требуется редкое подтверждение)
- `failed`
- `completed`

### 14.3 Контракт результата для пользователя

После успешного provisioning пользователь всегда получает:

- имя и назначение ассистента;
- где он доступен (личка/группа/топики);
- краткую инструкцию «как использовать»;
- кнопку/ссылку «Открыть ассистента»;
- статус здоровья (`ready`).

### 14.4 Продуктовые гарантии

- Один ассистент = одна чёткая задача (узкий фокус).
- Повторяемость: одинаковый шаблон даёт предсказуемый результат.
- Прозрачность: пользователь видит прогресс (`Настраиваю 3/7...`), а не «тишину».
- Безопасность: пользователь не получает инфраструктурные секреты.

### 14.5 Техническая реализация в рамках текущей архитектуры

Встраивается в существующие слои так:

- `Bot Edge` — UX-диалог «создай ассистента».
- `Policy` — решает, по какому маршруту работает созданный ассистент (`paid_api`/`free_ollama`).
- `Async workers` — выполняют provisioning шаги и ретраи.
- `OpenClawAdapter` — применяется там, где нужен agent/tool-runtime.

Важно:
- provisioning должен быть асинхронным и идемпотентным;
- любой шаг можно безопасно повторить;
- ошибки шагов возвращаются пользователю человеческим сообщением.

### 14.6 Явное соответствие сущностей Orchestrator

Минимальный mapping в текущем MVP:

- `assistant_instances`
  - что хранит: один созданный ассистент пользователя;
  - ключевые поля: `id`, `owner_user_id`, `title`, `template_key`, `status`, `created_at`, `updated_at`;
  - назначение: источник для списка в `/my_assistants`.
- `provision_jobs`
  - что хранит: один запуск provisioning (очередь + итог);
  - ключевые поля: `id`, `assistant_instance_id`, `owner_user_id`, `status`, `requested_payload`, `error_message`, `created_at`, `updated_at`, `finished_at`;
  - назначение: состояние асинхронной операции, которое возвращается в `/jobs`.
- `provision_steps`
  - что хранит: трассировку шагов внутри `provision_jobs`;
  - ключевые поля: `id`, `job_id`, `step_key`, `status`, `attempt`, `started_at`, `finished_at`, `details_json`;
  - назначение: диагностика и отладка в runbook.

Правило связей:
- один `assistant_instances` -> много `provision_jobs`;
- один `provision_jobs` -> много `provision_steps`.

### 14.7 Минимальный контракт команд/эндпоинтов

MVP поддерживает Telegram-команды как первичный интерфейс; HTTP-обёртка может повторять тот же контракт без изменения semantics.

`/create_assistant`
- вход: текст задачи (и опционально `template_key`);
- действие: создаёт запись `assistant_instances` со статусом `provisioning`, ставит `provision_jobs` в очередь (`queued`);
- ответ пользователю: `assistant_id`, `job_id`, текущий `job_status`.

`/my_assistants`
- вход: без параметров;
- действие: читает `assistant_instances` текущего `owner_user_id`;
- ответ пользователю: список ассистентов (`assistant_id`, `title`, `status`, `updated_at`).

`/jobs`
- вход: опционально `job_id` (если не передан — последние N job текущего пользователя);
- действие: читает `provision_jobs` + агрегирует последний step из `provision_steps`;
- ответ пользователю: `job_id`, `assistant_id`, `status`, `last_step`, `updated_at`, `error_message` (если есть).

### 14.8 Lifecycle provisioning (state diagram, текст)

Базовый переход статусов `provision_jobs`:

```text
queued -> running -> completed
                \-> failed
running -> needs_input -> running
```

Операционные правила:
- переход в `running` делает worker при фактическом старте job;
- `needs_input` используется только когда оркестратор ждёт подтверждение/данные от пользователя;
- из `failed` повторный запуск создаёт новый `provision_jobs` (история не перезаписывается);
- при `completed` связанный `assistant_instances.status` становится `ready`.
